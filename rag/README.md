# 약관 RAG

LLM 설명(지표 해석, 질문 답변, 증빙 요청서, 판단 불가 보완)에 관련 표준약관 조항을 함께 넣어, 근거 조항을 인용하게 합니다.
**약관은 인용에만 쓰고 점수, 위험도, 결과 제안은 바꾸지 않습니다.**

## 파일

| 파일 | 내용 |
|---|---|
| `source/terms_auto_silson_excerpt.pdf` | 원문. 「보험업감독업무시행세칙」 [별표15] 표준약관(국가법령정보센터) 492쪽 중 자동차보험(개인용, 원본 78~143쪽)과 실손의료보험 기본형·특별약관1·2(원본 204~313쪽)만 발췌한 176쪽 |
| `chunk_terms.py` | 원문 PDF를 조항(제○조, 별표, 붙임) 단위로 자르고 읽기 좋게 정리하는 스크립트 (아래 '원문 정리') |
| `terms_chunks.jsonl` | 자른 결과 196조각 (한 줄 = 한 조각) |
| `../terms-rag.mjs` | 조각에서 관련 조항을 고르는 모듈 (`person-llm.mjs`가 사용) |

기준 버전: 자동차보험 2026.8.28. 개정, 실손의료보험 2026.5.6. 개정 반영본.

## 원문 정리

PDF에서 뽑은 글자를 그대로 쓰면 쪽 너비에서 끊긴 줄바꿈("보상하지 않\n습니다")과 표 칸 글자가 본문 사이에 섞여 화면에서 깨져 보입니다. `chunk_terms.py`가 다음처럼 정리합니다.

- **줄 잇기**: 항(①), 호(1.), 목(가.), 문장 끝에서만 줄을 바꾸고 나머지는 잇습니다. 띄어쓰기는 자동차 약관은 원문 줄 끝 공백으로 정합니다. 실손 약관(원문에 공백 문자가 거의 없음)은 본문 단어 빈도로 정합니다.
  - 앞뒤가 둘 다 단어이면, 붙인 꼴이 본문에 있을 때 붙이고(지급|합니다, 과실|상계) 없으면 띄웁니다(보험금을|청구하여야).
  - 한쪽이 처음 보는 조각이면, 이어 붙인 앞부분으로 시작하는 단어가 있을 때 붙입니다(이|전인, 통원의|료비).
  - 조사·어미 조각(을, 으로, 일 등)과 한 글자 조각(및·등·그 같은 한 글자 단어 제외)은 붙이고, 쉼표 뒤는 띄웁니다.
  - 원문 줄 끝 공백은 있으면 띄우는 근거로만 씁니다(자동차 약관도 단어 끝에서 공백이 자주 빠져 있어, 없다고 붙이면 "인한손해에"처럼 됨).
  - 무작위 120곳을 직접 판정한 결과 줄 잇기 오류는 약 3%입니다(불리|하거나, 초과|되었을처럼 빈도로 구분이 안 되는 경우). 매핑 조항은 사전으로 0%.
- **실손 조항 표 왼쪽 칸**: 보장종목 이름("(1) 상해급여")을 그 칸 첫머리에 `[보장종목: (1) 상해급여]` 줄로 넣습니다.
- **붙임(용어 | 정의 표)**: PDF의 표 가로선으로 행을 나눠 `용어: 정의` 한 줄씩으로 만듭니다.
- **◦ 표(자동차 제27조·제31조 제출 서류)**: 표 세로선으로 칸을 나눠 `서류 (필요한 보장종목, ...)` 한 줄씩으로 만듭니다. 같은 높이의 글자 조각은 왼쪽부터 잇고(7번 ｢대인배상Ⅱ｣), 하위 서류마다 ○가 있으면 `- 서류 (보장종목)`으로 나눕니다(8번 전손 서류).
- 오른쪽 여백의 개정 표기 조각("<신설", "2026.5.6.>")과 표 머리글("보장종목 | 보상하는 사항", "용어 | 정의")은 뺍니다.
- 표 왼쪽 칸 판정은 PDF 표 가로선 안의 줄에만 씁니다(표 없는 쪽은 본문이 왼쪽 여백에서 시작해 짧은 줄을 칸으로 오인하기 때문).
- **숫자 표**: PyMuPDF 표 인식(`find_tables`)으로 찾은 3칸 이상 표 중 깔끔하게 옮겨지는 것(머리글이 채워져 있고, 칸이 120자 이하이고, 같은 글이 여러 칸에 반복되지 않음)은 마크다운 표로 저장합니다. 칸 글자는 표 인식 결과가 아니라 위의 띄어쓰기 복원·줄 잇기 규칙으로 뽑습니다. 현재 붙임2(적립이율), 실손 제30조·특약1 제6조·특약2 제6조(보험료 예시·할인할증) 5개입니다. 표가 조각 사이에서 나뉘면 다음 조각에 머리글을 다시 붙입니다. 화면 '조항 원문 보기'는 이 표를 HTML 표로 보여 줍니다.
- 조건을 못 넘는 표(별표1 지급 기준 같은 긴 글 상자, 특약 제2조 3칸 용어 표)는 한 문단으로 이어집니다(글자는 모두 남아 있음).
- **띄어쓰기 예외 사전(`FIXES`)**: 규칙으로 못 고치는 곳을 사전으로 고칩니다. 화면에 자동으로 붙는 매핑 조항(실손 제4조·제7조·붙임1, 자동차 제27조·별표3 기왕증 항목)은 사람이 전문을 읽고 검수해 사전에 넣었습니다. 항목을 더할 때는 원문 전체에서 그 위치에만 나오는지 확인합니다.
- 날짜("’26.5.6.")로 끝난 줄은 문장 끝으로 보지 않고 다음 줄과 잇습니다.

검증: 정리 전 조각과 조항별로 글자를 대조해, 빠진 글자는 개정 날짜·표 머리글·◦ 표시뿐이고 본문 글자는 모두 남아 있음을 확인했습니다.

정리 전 6,902줄(3글자 이하 토막 775줄) → 정리 후 약 1,730줄(12줄).

## 조각 형식

```json
{"id":"T0134","doc":"실손의료보험 표준약관(기본형)","section":"제9관 다수보험의 처리 등",
 "article":"제37조","title":"다수보험의 처리","kind":"article","page":245,
 "cite":"실손의료보험 표준약관(기본형) 제37조(다수보험의 처리), 별표15 245쪽","text":"제37조(다수보험의 처리) ① ..."}
```

- `page`: 원본 별표15 쪽 번호
- `kind`: article(조항), appendix(별표·붙임·부표), intro(약관 머리말)
- 1,500자가 넘는 조항은 여러 조각으로 나누고 `part_no`/`parts`로 표시합니다.

## 조항을 고르는 방법 (`terms-rag.mjs`)

1. **고정 매핑**: 코드 판정에 정해 둔 조항을 붙입니다. 같은 입력이면 같은 조항이 나옵니다.

   | 코드 판정 / 지표 | 조항 |
   |---|---|
   | 중복 확실, 중복 의심 | 실손 제4조(보상하지 않는 사항: 자동차보험에서 보상받는 치료관계비) |
   | 고지 확인 | 실손 붙임1(용어의 정의: 상해) |
   | 기왕증 (사고 전 같은 부위 진료 기록, 판정과 무관하게 연결마다) | 자동차 별표3(과실상계 등) 4. 기왕증 |
   | 판정 불가 | 실손 제7조(보험금의 청구), 자동차 제27조(제출 서류) |
   | 증빙 요청서, 판단 불가 보완 | 실손 제7조, 자동차 제27조 |

   한 번에 붙는 조항은 3개까지이며 위 표 순서가 우선입니다(기왕증은 서류 안내 조항보다 먼저).

   치료 기간 지표는 팀 기준(같은 사고 유형 집단 상위 5%)을 쓰므로 약관의 경상 4주 기준(자동차 별표1)을 자동으로 붙이지 않습니다. 담당자가 물으면 키워드 검색으로 찾습니다.

2. **키워드 검색**: 담당자 질문은 글자 2개 단위 BM25로 비슷한 조항을 찾습니다. 외부 모델이 필요 없습니다.
   - 표현 사전(`SYNONYMS`): 담당자 말투를 약관 용어로 넓힙니다(렌트카 → 대차료, 팔면 → 양도, 취소 → 청약의 철회 등). 원래 질문에 덧붙이기만 합니다.
   - 약관 구분: 질문에 실손·병원비·비급여 등이 있으면 실손 조항을, 자동차·운전·교통사고 등이 있으면 자동차 조항을 1.5배 우대합니다.
   - 조항 제목에 든 글자는 점수를 더 줍니다(제목이 곧 주제인 경우가 많음).
   - 점수 하한 15 미만이면 붙이지 않습니다("왜 보류인가요?" 같은 약관 밖 질문). 아래 평가로 정한 값입니다.

한 요청에 조항은 최대 3개입니다. LLM에는 매핑 조항은 사람이 쓴 **한 줄 요약 + 적용 문장**, 검색 조항은 **600자 발췌**를 보냅니다.

## 이 건에 어떻게 적용되는지 (적용 문장)

매핑 조항마다 코드가 이 사람의 근거 데이터로 적용 문장(`apply`)을 씁니다. 숫자와 번호는 근거 데이터에서만 나오고, 확정이 아니라 담당자가 확인할 내용으로 씁니다.

| 조항 | 적용 문장 예 |
|---|---|
| 실손 제4조 (중복 확실) | 사고 A0001(2025-03-02) 관련 청구 M0001: 같은 영수증의 치료비가 두 보험에서 모두 지급되었습니다(자동차보험 120,000원, 실손 120,000원). 자동차보험에서 보상받은 치료비는 실손에서 보상하지 않으므로, 실손 지급분이 이 조항의 보상 제외에 해당하는지 확인합니다. |
| 실손 제4조 (중복 의심) | 같은 병원·같은 치료 기간에 두 보험에서 비슷한 금액이 지급되었습니다. 같은 치료비라면 보상 제외에 해당하므로 서로 다른 비용 항목인지 확인합니다. |
| 자동차 별표3 (기왕증) | 사고 A0001 관련 청구 M0001: 사고 전 같은 부위 진료 기록(청구 M0009)이 있습니다. 사고 전부터 있던 증상으로 인한 손해는 보상하지 않고 사고로 악화된 부분만 기왕증 관여도를 빼고 보상하므로, 전문의 판정으로 관여도를 확인합니다. |
| 실손 붙임1 (고지 확인) | 사고로 생긴 손상 진료인데 실손에는 질병으로 청구되었습니다. 상해에 해당하면 상해로 다뤄야 하므로 사고 경위와 청구 구분을 확인합니다. |
| 실손 제7조, 자동차 제27조 (판정 불가) | 양쪽 영수증 번호가 비어 있어 같은 치료비인지 판정할 수 없습니다. 이 조항의 청구 서류(진료비 계산서·영수증 등)로 확인합니다. |
| 실손 제7조, 자동차 제27조 (요청서·보완, 판정 없음) | 요청할 서류는 이 조항이 정한 청구 서류 안에서 고릅니다. |
| 질문 검색 조항 | 담당자 질문으로 찾은 조항이며 코드 판정과 직접 연결된 조항은 아님을 표시합니다. |

같은 판정이 여러 건이면 3건까지 쓰고 나머지는 '외 n건'으로 줄입니다.
LLM은 '관련 약관: (조항) — (이 건에 어떻게 적용되는지)'를 apply 안에서만 씁니다.
화면의 '관련 약관'은 조항 이름 아래에 적용 문장을 보여 주고, '조항 원문 보기'를 누르면 조각 전문이 펼쳐집니다(LLM을 거치지 않은 원문).

## LLM 입력 줄이기

교차 연결 중 '정상 분리 청구'는 개수(`normal_link_count`)만 보냅니다. 기왕증 기록이 있거나 담당자 질문에 번호가 나온 연결은 상세를 보냅니다.
데모 설명과 검증은 줄이지 않은 전체 근거를 씁니다. 데모 500명 기준 근거 JSON 최대 5,884자 → 3,142자.

## 검증

LLM 응답의 `term_refs`(인용한 조항 ref)가 넣어 준 조항에 없으면 기존 수치 검증 실패와 같이 데모 설명으로 대체합니다.
LLM에 보낸 조항의 숫자(예: 제4조, 4주)는 지어낸 숫자로 보지 않도록 검증 범위에 넣었습니다. 브라우저 쪽 재검증(`person-app.js`)도 같은 방식입니다.

## 다시 만들기

```bash
pip install -r rag/requirements.txt
python rag/chunk_terms.py rag/source/terms_auto_silson_excerpt.pdf rag/terms_chunks.jsonl
```

표 인식 때문에 1~2분 걸립니다. 같은 PDF면 항상 같은 결과가 나옵니다.

조 번호 누락 여부를 출력합니다. 표(별표1 등)는 PDF 배치 때문에 일부 줄 순서가 섞일 수 있습니다.

참고: 현재 팀 데이터(`dist/data/insure.db`, `mock.json`)에는 엔진 기준 기왕증 판정이 0건이라 화면에서 별표3이 붙는 사람은 없습니다. 시연하려면 데이터에 사고 전 90일 안 같은 부위 진료 건이 필요합니다.

## 질문 검색 평가 (`rag/eval/`)

담당자 질문을 넣었을 때 맞는 조항이 나오는지 숫자로 잽니다.

| 파일 | 내용 |
|---|---|
| `questions.jsonl` | 개발용 50문항(약관 안 42, 약관 밖 8). 검색을 고칠 때 이것만 봅니다 |
| `questions_test.jsonl` | 검증용 32문항(약관 안 27, 약관 밖 5). 개선 전에 따로 써 두고, 개선이 끝난 뒤 한 번만 채점합니다 |
| `eval-search.mjs` | 채점 스크립트 |

- 정답은 조 단위입니다(같은 조의 여러 조각은 하나로 셈). 맞는 조항이 여러 개인 질문은 그중 하나만 나와도 정답입니다.
- 지표: Hit@1(1위가 정답), Hit@2(앱이 붙이는 2개 안에 정답), MRR@5, 약관 밖 질문 거름(아무 조항도 안 붙임).
- 비교(Baseline): 제목 매칭(질문 단어가 조항 제목에 있는지), 단어 BM25(띄어쓰기 단위), 글자 2개 BM25(현재 방식).

```
node rag/eval/eval-search.mjs           # 개발용
node rag/eval/eval-search.mjs --sweep   # 점수 하한별 표
node rag/eval/eval-search.mjs --test    # 검증용
```

결과 (2026-11-06)

| 검증용 32문항 | Hit@1 | Hit@2 | MRR@5 | 약관 밖 거름 |
|---|---|---|---|---|
| 제목 매칭 | 4% | 19% | 0.12 | 0% |
| 단어 BM25 | 33% | 41% | 0.43 | 0% |
| 글자 2개 BM25 (개선 전, 하한 8) | 63% | 70% | 0.70 | 20% |
| **글자 2개 BM25 + 표현 사전·약관 구분·제목 가중 (하한 15)** | **78%** | **78%** | **0.81** | **80%** |

| 개발용 50문항 | Hit@1 | Hit@2 | MRR@5 | 약관 밖 거름 |
|---|---|---|---|---|
| 개선 전 (하한 8) | 36% | 50% | 0.45 | 25% |
| 개선 후 (하한 15) | 71% | 79% | 0.77 | 88% |

- 점수 하한: 개발용에서 하한 14~16 구간이 Hit@2를 유지하면서 약관 밖 질문을 가장 많이 걸러, 구간 가운데인 15로 정했습니다.
- `npm test`는 개발용 기준 Hit@2 75% 이상, 약관 밖 거름 75% 이상, 비교 방식보다 나음을 확인합니다. 검증용은 발표 수치용이라 테스트에 넣지 않습니다.
- 한계: 질문과 정답을 한 사람이 만들었고 문항 수가 적습니다(검증용 27문항이면 1문항 = 약 4%p). 실제 담당자 질문으로 늘리면 수치가 달라질 수 있습니다. 검증용에서 놓친 질문은 "교통사고 치료비를 자동차보험으로 처리했는데 실손 청구도 들어왔다"(실손 제4조), "한의원 침 치료"(실손 제4조), "체외충격파 한도"(특약 제3조), "휴업손해 계산"(자동차 별표1), "뺑소니 차량"(자동차 무보험차 상해) 등입니다.

## 발췌 (검색 조항을 LLM에 보낼 때)

질문 검색으로 찾은 조항은 원문 전체가 아니라 400자만 보냅니다. 예전에는 조각 앞 600자를 잘랐는데, 질문과 관련된 내용이 뒤쪽에 있으면 빠졌습니다. 지금은 질문(표현 사전 포함)과 겹치는 글자가 가장 많은 구간을 고르고, 그 구간이 가운데 오도록 400자를 자릅니다(`excerpt()`).

| 발췌 방식 | 질문 관련 글자 보존 (평가 질문 66문항) | 길이 |
|---|---|---|
| 앞 600자 (예전) | 89% | 600자 |
| 앞 300자 | 76% | 300자 |
| 질문 맞춤 300자 | 86% | 300자 |
| **질문 맞춤 400자 (현재)** | **90%** | **400자** |

질문 답변 요청의 LLM 입력은 검색 조항 하나당 200자 줄어듭니다(질문 요청 전체 기준 약 4%). 매핑 조항은 원래 요약만 보내므로 변화가 없습니다.

## 약관 개정 대응

- **요약 근거 문구(`facts`)**: 매핑 조항의 한 줄 요약(`summary`)은 사람이 원문과 대조해 썼습니다. 요약이 근거로 삼은 원문 문구를 `facts`로 적어 두었고, `npm test`가 이 문구가 원문(띄어쓰기 무시)에 모두 있는지 확인합니다. 약관 PDF를 새 개정본으로 바꿔 조각을 다시 만들었을 때 테스트가 실패하면, 그 조항의 요약과 적용 문장을 원문과 다시 대조합니다.
- **띄어쓰기 예외 사전**: `chunk_terms.py`가 조각을 만들 때 한 번도 쓰이지 않은 예외 사전 항목이 있으면 "주의: 쓰이지 않은 띄어쓰기 예외 사전 항목"을 출력합니다. 개정으로 해당 글자가 바뀐 것이므로 원문을 다시 보고 사전을 고칩니다.
- 개정 시 순서: 새 PDF로 교체 → `python rag/chunk_terms.py …` 실행(경고 확인) → `npm test`(facts·매핑 확인) → `node rag/eval/eval-search.mjs`(검색 성능 확인).
